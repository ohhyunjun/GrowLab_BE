# AWS 기존 DB 전환 절차

코드만 먼저 배포하면 기존 `plant`에 품종이 없고, 일지·첨부 파일 구조와 새 엔터티가 달라 조회·저장에 실패할 수 있다. `spring.jpa.hibernate.ddl-auto=update`는 기존 데이터의 의미를 옮겨주지 않는다.

2026-09-22에 보관한 `schema_before_reset.sql`은 당시 백업이다. 이후 RDS가 초기화되었을 수 있으므로 **현재 RDS 스키마와 행 수를 새로 확인**해야 한다. 모든 테이블에 임의 값을 넣지 않는다. 변경 대상은 `device`, `plant`, `diary`, `file`이며, `image` 자료를 `file`로 복사한다. `sensor_anomaly`는 새 코드에서 사용하지 않지만 배포 직후에는 보존한다. 다른 테이블은 기존 데이터와 관계를 유지한다.

1. 구형 BE의 쓰기를 중지한다. RDS 스냅샷과 `mysqldump --single-transaction --routines --triggers` 논리 백업을 만들고 복원 가능한지 별도 DB에서 확인한다. RDS 백업과 별개로 첨부 파일·카메라 사진의 S3 객체도 보존한다.
2. 현재 RDS에서 `migrations/20261004_preflight.sql`을 **읽기 전용**으로 실행한다. 전체 테이블·컬럼·FK 목록과 주요 테이블의 정확한 행 수를 보관한다. 결과가 2026-09-22 스키마와 다르거나 식물의 기존 품종이 `NULL`, 일지의 식물 참조가 없음, 포트가 0~7 밖, `port_status`가 8자리가 아닌 행이 있으면 중단하고 행별로 원인을 확인한다. 임의 품종·종료 사유를 넣지 않는다.
3. 운영 DB와 같은 시점의 복제 DB에서 `20261005` → `20261006` → `20261007` → `20261008` 순으로 시험한다. MySQL DDL은 일반적인 트랜잭션 롤백 대상이 아니므로 각 단계 실패 시 부분 적용 상태를 확인하고 백업에서 다시 시작한다.
4. 복제 DB에서 기존 `device.species_id`가 각 `plant.species_id`로 이전됐는지, 기존 일지의 `plant_id`와 기기·포트 스냅샷이 맞는지, 활성 포트 유일성이 유지되는지 확인한다. `file.file_url`은 기존 S3 주소를 유지해야 한다. `image`의 모든 행이 `file`에 대응하는지와 전후 행 수를 확인한다. `image`·`sensor_anomaly`는 이 단계에서 삭제하지 않는다.
5. 검증한 절차를 운영 RDS에 적용한 뒤 새 BE를 먼저 배포하고, 기기·식물·일지·사진·첨부 파일·알림을 점검한 후 FE를 배포한다. 애플리케이션을 다시 쓰기 가능하게 열기 전에 오류와 데이터 건수를 확인한다.
6. 문제가 있으면 구형 BE·FE와 DB 백업으로 복구한다. 사용하지 않는 `image`, `sensor_anomaly`의 물리적 삭제는 운영 검증과 백업 보관이 끝난 별도 작업으로 진행한다.

## 상추 수확일 기능의 추가 변경 (2026-10-19 점검)

위 20261005~08 전환과 구분되는 **추가 migration**이다. 2026-10-19 운영 RDS를 읽기 전용으로 확인했을 때 MySQL 8.4.8, `photo` 780행, `plant` 13행, 기존 `prediction` 3152행, `sensor_anomaly` 144행이었다. 새 `photo.plant_id/captured_at/observation_id`와 `harvest_prediction`은 아직 없었다. 이 숫자는 점검 시점의 값이며 적용 직전 다시 기록해야 한다.

1. 기존 BE 쓰기를 멈추고 RDS 스냅샷·논리 백업 및 복원 확인을 먼저 수행한다. 사진의 S3 객체도 보존한다. MySQL DDL은 일반 트랜잭션처럼 되돌릴 수 없다.
2. 기존 `photo`, `plant`, `prediction` 행 수와 스키마·인덱스를 기록한다. `migrations/20261018_edge_harvest.sql`을 복제 DB에서 먼저 실행하고 재실행해 부분 적용 복구 경로를 검증한다. `ddl-auto=update`만으로 이 절차를 대신하지 않는다.
3. 운영 DB에는 기존 `photo`의 nullable 컬럼·인덱스 및 새 `harvest_prediction` 테이블만 추가한다. 기존 사진과 단계 예측 행은 UPDATE/DELETE하지 않는다. 과거 사진은 새 식별자 세 개가 `NULL`인 채 유지된다.
4. 적용 후 `migrations/20261018_edge_harvest_verify.sql`로 행 수, 새 컬럼, 인덱스, FK를 확인한다. 백업 전의 기존 행 수와 비교한다. 그다음 새 BE, FE, RPi 순서로 적용하고 과거 사진 조회·새 사진 업로드·새 수확일 조회를 각각 검증한다.

기존 사진을 새 재배 ID로 일괄 채우지 않는다. 점검 시점의 780장 중 촬영 시각·기기·포트가 현존 `plant` 재배 기간에 한 개만 겹치는 사진은 560장이고, 220장은 해당 재배 기록이 없다. 560장도 시간 조건만으로 개체가 확정된 것은 아니다. BE의 성장 추이 화면은 과거 사진의 `plant_id`가 없으면 기간과 포트로 **조회 시** 연결하며, 재배가 확인되지 않는 사진은 기기 사진 기록으로만 남긴다. 과거 사진에는 275차원 영상 특징과 관측 ID가 없으므로 새 수확일 예측 행을 소급 생성하지 않는다.

**현재 상태:** 위 추가 migration은 운영 RDS에 적용되지 않았다. 코드·EC2 모델 준비와 운영 BE/FE/DB 적용을 혼동하지 않는다.
